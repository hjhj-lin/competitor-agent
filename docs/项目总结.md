# 竞品分析多Agent平台 — 项目总结

## 一、项目概览

基于Spring AI + 多Agent协作的企业竞品分析平台，4个AI Agent串行编排，自动完成竞品信息采集→深度分析→审核校验→报告生成全流程。

## 三、技术亮点（面试重点）

### 亮点1：模板方法模式 + 多Agent编排

**问题**：4个Agent逻辑相似（构建prompt→调用AI→解析结果），但细节不同。
**方案**：`BaseReActAgent`抽象基类定义`execute()`骨架，子类只需实现3个抽象方法：
- `buildQuestion()` — 构建用户提问
- `getResultKey()` — 结果存储key
- `getModelName()` — 模型选择（可选覆盖）

**面试话术**：
> "我用模板方法模式抽象了4个Agent的公共执行流程，子类只需关注差异部分。新增Agent只需实现3个方法，5分钟就能接入Pipeline。"

### 亮点2：流式Token输出 + SSE实时推送

**问题**：AI生成报告耗时30-60秒，用户等待体验差。
**方案**：`chatClient.stream().content().doOnNext()`逐Token推送，SSE分3种事件类型：
- `agent` — Agent切换通知
- `content` — Token级内容
- `result` — 最终结果

**面试话术**：
> "我实现了Token级流式输出，用户能实时看到AI的思考过程，感知延迟从60秒降到首Token 2秒内。SSE三种事件类型让前端能区分Agent切换和内容推送。"

### 亮点3：Resilience4j熔断 + 降级策略

**问题**：外部API（Tavily搜索、DeepSeek AI）不稳定，失败会阻塞整个Pipeline。
**方案**：
- `tavily`熔断器：搜索失败→降级走DeepSeek生成
- `aiCall`熔断器：AI调用失败→触发Pipeline重试
- 滑动窗口10次，失败率50%开启，30秒后半开

**面试话术**：
> "我设计了双层熔断保护：搜索API熔断后降级到AI生成，AI调用熔断后触发Pipeline指数退避重试。确保单点故障不会拖垮整个系统。"

### 亮点4：Prompt外部化 + 热更新

**问题**：Prompt硬编码在Java类中，调优需要重启服务。
**方案**：`prompt_template`表 + `PromptService` + Caffeine 5分钟缓存 + REST API热更新。

**面试话术**：
> "我把Prompt从代码中解耦到数据库，配合Caffeine缓存实现5分钟延迟生效的热更新。运营人员可以通过API调优Prompt，无需开发介入。"

### 亮点5：多模型per-request切换

**问题**：不同Agent对模型能力需求不同，单一模型无法兼顾成本和效果。
**方案**：`OpenAiChatOptions.builder().model(name)` per-request覆盖 + `@ConditionalOnProperty`条件注册Kimi ChatClient + `useKimi()/getActiveChatClient()`双模型切换。

**面试话术**：
> "我设计了per-request模型切换机制，采集/分析用轻量模型降成本，审核/报告用强模型保质量。还预留了Kimi等国产模型的即插即用能力，条件注册确保无Key时不影响启动。"

### 亮点6：API限流 + 成本控制

**问题**：AI调用按Token计费，需要防止滥用。
**方案**：`@RateLimit`自定义注解 + Caffeine滑动窗口限流 + `ai_usage_daily`表100次/天限制。

**面试话术**：
> "我设计了双层成本控制：Caffeine滑动窗口限流防并发滥用，数据库日用量统计防超额消费。自定义注解让限流配置声明式化，一行代码即可保护任何端点。"

```
用户输入公司名
  → TaskController.createTask()
    → PipelineExecutionService.executeAsync()
      → AgentPipeline.execute()
        → CollectAgent(采集) → AnalyzeAgent(分析)

```

## 七、面试高频问题预案

**Q: 为什么用模板方法而不是策略模式？**
A: 4个Agent的执行流程完全相同（构建prompt→调用AI→解析结果→SSE推送），只是构建问题的方式和结果key不同。模板方法更自然——定义不变的上层流程，子类只实现变化的部分。策略模式适合算法可替换的场景，这里没有替换需求。

**Q: SSE和WebSocket怎么选？**
A: SSE是单向推送（服务器→客户端），适合AI流式输出这种"只读"场景。WebSocket是双向通信，适合聊天室等需要客户端也发消息的场景。我们只需要服务端推送Token，SSE更简单、更轻量、原生支持断线重连。

**Q: 熔断和限流有什么区别？**
A: 熔断是保护下游——当下游服务故障率过高时，主动断开避免雪崩。限流是保护自身——限制请求速率防止过载。我们两层都有：Resilience4j熔断保护Tavily/AI调用，@RateLimit限流保护API端点。

**Q: Caffeine和Redis缓存怎么选？**
A: 单机部署用Caffeine（本地缓存，零网络开销），集群部署用Redis（分布式共享）。我们当前是单机，Prompt缓存用Caffeine 5分钟过期，限流计数也用Caffeine 1分钟窗口。如果未来需要多实例部署，限流需要迁移到Redis。
